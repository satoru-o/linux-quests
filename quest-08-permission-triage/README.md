# quest-08: permission-triage

前提セットアップは不要。ビルドしてすぐ挑戦できる。

## これは何か

[quest-07](../quest-07-network-triage/)と同じ**診断ドリル**の権限版。`./new-case.sh`を叩くたびにランダムな故障が1つ仕込まれ、原因を突き止めて`./answer.sh`で申告する。修理ではなく診断が目的。

権限まわりは「`Permission denied`と出た → ファイルのモードを見る → 合ってるように見える → 詰まる」という誤診が起きやすい。実際には**そのファイルまで辿り着けているか**や、**そもそも権限ビットの話なのか**を先に確かめる必要がある。そこを型にする。

## 正常な状態

`work`コンテナの中で`appuser`として、`/data`の定常業務が最後まで通るのが正常。

```bash
docker compose exec work /job.sh
```

4つの操作(一覧・読み取り・書き出し・後始末)を順に試して、それぞれOK/NGを表示する。症例が仕込まれている間は、どれかがNGになる。

## 診断の型

**「誰が」「何に」「どこを通って」触ろうとしているかを、順に確定させる。**

| 段 | 問い | コマンド | 分かること |
| --- | --- | --- | --- |
| 1 | 自分は誰か | `docker compose exec work id` | UID/GIDと**所属グループの一覧** |
| 2 | 対象の所有者とモードは | `docker compose exec work ls -l /data/report.txt` | 所有者・グループ・rwxビット |
| 3 | そこまで辿れるか | `docker compose exec work namei -l /data/report.txt` | **経路上の全ディレクトリ**のビット |
| 4 | エラーは何と言っているか | `/job.sh`の出力をそのまま読む | errnoの違い(下の表) |
| 5 | 権限ビットの外側は | `docker compose exec work mount \| grep /data` | `ro`かどうか |

第3段が肝心。ファイルのモードがどれだけ緩くても、**途中のディレクトリに`x`が無ければ辿り着けない**。`ls -l`だけ見て「権限は合ってるのにおかしい」となるのは、たいていこれ。

### エラー文の読み分け

見た目が似ていても、意味する層がまったく違う。

| エラー文 | errno | 疑うもの |
| --- | --- | --- |
| `Permission denied` | EACCES | 権限ビット。**対象自身か、経路のディレクトリか**の両方を見る |
| `Operation not permitted` | EPERM | ビットでは説明できない禁止。stickyビット、所有者限定の操作など |
| `Read-only file system` | EROFS | **権限の話ではない。** マウントが読み取り専用 |

`Read-only file system`が出ているのに`chmod`で直そうとするのは典型的な迷走なので、ここは覚えてしまってよい。

### できること/できないことの組み合わせで割る

| 一覧(ls) | 読み取り(cat) | 書き出し | 疑うもの |
| --- | --- | --- | --- |
| OK | NG | OK | 対象ファイル自身(所有者・グループ・ビット)。`id`と`ls -l`を突き合わせる |
| NG | **OK** | NG | ディレクトリの`r`が無い(名前が見えないだけで、パスが分かれば読める) |
| 全部NG | NG | NG | ディレクトリの`x`が無い(そもそも通れない) |
| OK | OK | NG | ディレクトリの`w`が無い、またはマウントが`ro`。**errnoで割る** |

一覧がNGでも読み取りがOKになる、という組み合わせが存在するのが権限の面白いところ。`r`(名前を読む)と`x`(通り抜ける)が別のビットだから起きる。

## 使い方

```bash
./new-case.sh          # 新しい症例を仕込む(何が仕込まれたかは表示されない)
```

型に沿って診断する。分かったら申告する。

```bash
./answer.sh --list     # 申告できる原因の一覧
./answer.sh <原因ID>   # 申告する
./answer.sh --giveup   # 降参して答えを見る
```

## 申告できる原因

| 原因ID | 内容 | 該当する段 |
| --- | --- | --- |
| `not-owner` | 対象が他人の所有で、自分に許可が無い | 2 |
| `group-not-member` | グループには許可があるが、自分がそのグループに所属していない | 1と2の突き合わせ |
| `no-read-bit` | 自分が所有者だが、読み取りビットが落ちている | 2 |
| `dir-no-exec` | 親ディレクトリに`x`が無く、パスを辿れない | 3 |
| `dir-no-read` | 親ディレクトリに`r`が無く、一覧が取れない | 3 |
| `dir-no-write` | 親ディレクトリに`w`が無く、作成・削除ができない | 3 |
| `sticky-other` | stickyビットのあるディレクトリで、他人のファイルを消せない | 3 |
| `readonly-mount` | 権限ビットではなく、マウントが読み取り専用 | 5 |

上3つは`/job.sh`の見た目がまったく同じになる。**`id`と`ls -l`を突き合わせないと割れない**ので、そこが練習どころ。

## 続け方

日を空けて何度か回すのがおすすめ。「`Permission denied`を見た瞬間に`namei`が手癖で出る」ようになったら身についている。
